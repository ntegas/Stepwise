# DEVELOPMENT_PROTOCOL.md — Code Architecture Centralization Rules

Binding rules for how Stepwise's code must be structured, so that "complex inside, simple every day" (`/PRODUCT_CANON.md` §2) holds at the code level too. **Core principle: any logic that could give a different answer in different parts of the app must have exactly one canonical implementation.** Where a rule is already elaborated in detail elsewhere, this document states the rule and points there rather than re-deriving it — per the anti-duplication discipline in `/ANTI_ERROR_STANDARD.md`, this document is not exempt from its own rule 49.

## A. Domain & execution centralization

1. **One canonical calculation, everywhere.** Today, Progress, and the Widget must never compute Goal Progress (or any other business metric) by three different formulas. UI/Widget/Notification → shared domain Use Case → canonical calculation logic. Detail: `/ARCHITECTURE.md` §12, §15.
2. **Canonical domain models**, separate from Room entities, Supabase DTOs, and Compose UI models: `Database Entity → Mapper → Domain Model → UI Model` where needed. Detail: `/ARCHITECTURE.md` §6.
3. **Repository contracts**: feature/domain code never touches Room DAOs, Supabase, HTTP, or DataStore directly — only repository interfaces (`GoalRepository`, `SessionRepository`, `ActivityRepository`, `TaskRepository`, …). Detail: `/ARCHITECTURE.md` §4, §27.
4. **One canonical execution engine.** Done from Today, an Activity, a Habit, the Widget, or a Notification action all flow through one `CompleteOccurrenceUseCase` → canonical transaction → Session/execution fact → recalculation → sync. No per-surface execution logic, ever. Detail: `/ARCHITECTURE.md` §19.3 (established for the Widget; binding for every surface, present and future).
5. **Calculation Engine centralizes**: Goal Progress, Planned vs Actual, Execution, Pace, Forecast, Goal Impact, Activity/Life Area statistics, Life Balance, period comparisons, Week/Month/Year/All-Time aggregation. UI displays results, never computes business metrics itself. Content: `/CALCULATION_ENGINE.md` (scaffolded, filled in its own phase per `/PROJECT_STATE.md`).
6. **Today Aggregation Engine**: one `GetTodayAgendaUseCase` merges Tasks, Activities, Habits, virtual recurring occurrences, deadlines, and scheduled items into one model. Today Screen and the Widget both consume it unchanged. Detail: `/ARCHITECTURE.md` §14, §19.7.
7. **Recurrence Engine**: one component owns recurrence rules, virtual occurrences, stable occurrence identity, exceptions, reschedule, skip, materialization, and next-occurrence resolution. Never reimplemented separately inside Task, Habit, or Calendar UI. Detail: `/ARCHITECTURE.md` §13, B3/B9.
8. **Timer Engine**: one authoritative Timer state regardless of origin (Activity screen, Today, Widget, Notification) — modeled as a `Session` in `IN_PROGRESS` status, not a separate mutable entity. Detail: `/ARCHITECTURE.md` §19.8.
9. **Status Architecture**: execution statuses (Done/Partial/Missed/Rescheduled/In Progress/Cancelled) and lifecycle statuses (Active/Paused/Completed/Archived) are typed enums, never raw strings like `"completed"` scattered through the codebase. Detail: `/ARCHITECTURE.md` §6, concept §13/§25.
10. **Database ownership**: each table/entity has one owning module (e.g. the Session module owns Session semantics). Other features read through public contracts; they never silently change another module's entity semantics.

## B. Data & sync centralization

11. **Date/Time architecture**: one `Clock` abstraction, one place for timezone, current date/time, day/week/month/year boundaries, date/duration formatting, and recurrence time math. No raw `now()` calls scattered through the app; `Clock` must be fakeable in tests.
12. **Metrics and Units**: one system for time/distance/count/pages/currency/weight/percentage/custom units, with centralized conversion and formatting (e.g. `3600 sec → domain duration → "1h"` computed once, not per-screen). Detail: `/ARCHITECTURE.md` §19.1 (metric catalog), `/DATA_MODEL.md`.
13. **Sync Engine**: sync queue, retries, backoff, versions, conflict handling, tombstones, idempotency, upload/download order, and sync status are all centralized. No feature pushes changes to the backend outside the Sync Engine. Detail: `/ARCHITECTURE.md` §9.
14. **Transactions**: critical multi-step operations (e.g. Complete Task) define their transaction boundary up front — never leave `Task = Done` with no Session, or a Session with an un-transitioned occurrence. Detail: `/ARCHITECTURE.md` §19.3, and the Transaction Boundaries elaboration folded into `/ARCHITECTURE.md` per the Security/Transaction/Concurrency standard.
15. **Concurrency**: double-tap, two devices, simultaneous edits, offline edits, duplicate requests, and retry-after-timeout are all defined architecturally before implementation, not patched in after a bug report. Detail: `/ARCHITECTURE.md` §9 (hybrid conflict resolution, B7), §19.4 (local idempotency).
16. **Migration Architecture**: any database semantics change requires a schema migration, backward-compatibility analysis, affected-consumer inventory, a migration test, and rollback/data-loss consideration. No destructive migrations without an explicitly agreed reason. Detail: `/ARCHITECTURE.md` §25.
17. **Cache / derived data**: canonical data, derived data, cache, and materialized analytics are explicitly distinguished up front. Derived values never become a second independent source of truth; invalidation/recalculation rules are defined, not assumed. Detail: `/ARCHITECTURE.md` §7, §15, `/DATA_MODEL.md`.
18. **Error Architecture**: one error model (`DomainError`/`ValidationError`/`DatabaseError`/`NetworkError`/`AuthError`/`SyncError`/`BillingError`); infrastructure errors are translated to domain-level errors before the UI sees them. Detail: `/ARCHITECTURE.md` §23.
19. **Validation Architecture**: business validation (deadline validity, negative duration, invalid target, invalid recurrence, duplicate Session, impossible metric value) lives outside the UI. A Compose form displays errors; it does not own the rule.

## C. UI / presentation centralization

20. **Design System**: colors, typography, spacing, shapes, corner radius, elevation, icon sizing, animation, component states, light/dark theme, and semantic colors are all centralized tokens, not per-screen constants. Reusable components: `StepwiseButton`, `StepwiseCard`, `StepwiseGoalCard`, `StepwiseTaskRow`, `StepwiseActivityRow`, `StepwiseProgressIndicator`, `StepwiseChip`, `StepwiseDialog`, `StepwiseTopBar`, `StepwiseBottomNavigation`, `StepwiseEmptyState`, `StepwiseLoadingState`, `StepwiseErrorState`. Content: `/DESIGN_SYSTEM.md` (scaffolded, filled in its own phase).
21. **Navigation Architecture**: one source of truth for destinations, routes, deep links, argument definitions, and navigation contracts. Feature modules never invent an incompatible navigation scheme; the Widget and Notifications use the same destinations/deep-link contracts as normal UI. Detail: `/ARCHITECTURE.md` §19.3, §19.13 (deep links reused, not duplicated).
22. **State Management**: `Repository/Use Case → StateFlow → ViewModel → Compose UI`, one direction. The UI never owns canonical business state; the ViewModel is a screen/application state holder, not a second repository. Detail: `/ARCHITECTURE.md` §4.
23. **Accessibility** is a Design System concern from the start (scalable text, content descriptions, touch target sizes, contrast, screen readers, reduced motion) — not retrofitted per screen.
24. **Adaptive UI**: not hard-coded to one phone size — phones, large phones, tablets, orientation where relevant, and Android window size classes are accounted for architecturally.
25. **Localization**: every user-facing string lives in the resources/localization layer, never hardcoded in Compose. Pluralization, number/date/currency formatting, and variable text length are accounted for. Decision already locked: i18n from day one, Russian + English minimum (`/PRODUCT_CANON.md` decisions).

## D. Cross-cutting infrastructure

26. **Background Work**: all background operations (sync, reminders, recurrence maintenance, widget refresh, analytics upload, cleanup) go through a centralized scheduler abstraction; Domain depends on that abstraction, never on `WorkManager`/`AlarmManager`/FCM directly. Detail: `/ARCHITECTURE.md` §18 (`ReminderScheduler` — the established pattern this rule generalizes).
27. **Notifications**: notification channels, IDs, reminder logic, actions, deep links, scheduling, and cancellation are centralized. A Notification's `Done` action uses the same execution pipeline as Today and the Widget (rule A4). Detail: `/ARCHITECTURE.md` §18, §19.
28. **Search**: one search abstraction across Goals/Tasks/Activities/Habits/History — not an independent implementation per entity. Searchable entities, indexing, ranking, and offline behavior defined once. Detail: `/ARCHITECTURE.md` §17.
29. **Analytics / Events**: a canonical event catalogue (`task_completed`, `session_created`, `goal_completed`, `timer_started`, `timer_stopped`, …), with a `source: APP | WIDGET | NOTIFICATION` metadata field that never changes domain semantics. Detail: `/ARCHITECTURE.md` §19.12.
30. **Configuration / Feature Flags**: one configuration layer for experimental features, staged rollout, temporary disable, backend-controlled options, and local developer flags — never scattered boolean constants.
31. **Permissions**: centralized handling (notifications, calendar integration, future health integrations) — feature screens never implement their own permission flow.
32. **Authentication / User Session**: one Session/Auth manager owns authentication state, current user, logout, token refresh, and deleted-account state. Feature modules never talk to the auth provider directly. Detail: `/ARCHITECTURE.md` §11, `/docs/security/SECURITY_ARCHITECTURE.md`.
33. **Billing / Entitlements**: one authoritative entitlement layer; the UI never interprets raw Google Play purchase state itself. Detail: `/ARCHITECTURE.md` §19 (Billing Architecture section).
34. **Deep Links / External Entry Points**: every external entry point (Widget, Notification, future links, shortcuts) routes through the centralized routing layer (rule C2) — no bespoke entry-point routing.
35. **Export / Import / Backup**: the data architecture doesn't block user export, account deletion, restore, or a future backup strategy; export format is decoupled from the internal Room schema.

## E. Engineering process & operations

36. **Environment / Secrets**: local/dev, staging, and production are separated; no secrets in the repository; backend URLs, build config, and feature switches are centrally managed. Detail: `/docs/security/SECURITY_ARCHITECTURE.md`, `/docs/security/AI_CODE_SECURITY.md`.
37. **Dependency Management**: one dependency version catalog; no module sets library versions independently. Detail: `/docs/security/DEPENDENCY_POLICY.md`.
38. **Module Dependency Rules**: dependency direction is defined up front (`feature → domain → repository contracts`; `infra/data → implements repository contracts`); Feature A never depends on Feature B's internals; shared logic moves to the appropriate core/domain module; no cyclic dependencies. Already enforced: `/ARCHITECTURE.md` §27.
39. **Performance Boundaries**: expensive operations never run on the UI thread; large aggregations aren't recomputed unnecessarily; lists use paging/lazy rendering where needed; database indexes follow real query patterns; widget/background work respects battery. Detail: `/ARCHITECTURE.md` §22.
40. **Security Architecture** and **Privacy Architecture**: cross-cutting, not a post-development pass. Detail: `/docs/security/SECURITY_ARCHITECTURE.md` (full standard) — covers authentication, authorization, RLS, ownership, input validation, secure storage, secrets, account deletion, export/delete, and what the Widget is allowed to show.
41. **Testing Architecture**: centralized test utilities (fake `Clock`, fake repositories, test builders, fixture factories, fake sync engine, fake scheduler); unit/repository/database/integration/UI/migration/sync-conflict tests kept distinct; Acceptance Criteria ↔ Tests = 1:1 for substantial changes (`/ANTI_ERROR_STANDARD.md` §6). Detail: `/ARCHITECTURE.md` §24.
42. **Static Analysis / Quality Gates**: one formatter, lint config, Kotlin static analysis, dependency check, and test suite, run locally and in CI.
43. **CI/CD**: `commit/PR → format/lint → unit tests → database/migration tests → build → UI/integration tests where relevant → release artifact`. Production deployment never depends on an ad hoc manual command sequence. Detail: `/docs/security/SECURITY_TEST_MATRIX.md` for the security-specific gate additions.
44. **Logging / Observability**: one logging abstraction; no bare `println`; debug/error/crash/sync-diagnostics/performance logs distinguished; sensitive data never logged. Detail: `/ARCHITECTURE.md` §26, `/docs/security/SECURITY_ARCHITECTURE.md` §24 (logging security specifics).
45. **Code Ownership / Public Interfaces**: every module has a clear responsibility, a public API, and internal implementation not exposed wholesale; other modules interact only through contracts.

## F. Governance

46. **Architecture Decision Records**: every significant decision is recorded as its own file under `/ADR/` (e.g. `ADR-001-native-android.md`, `ADR-002-supabase.md`, …) — so a future session can't accidentally revisit a settled decision without seeing why it was made.
47. **Canonical Documentation**: `PRODUCT_CANON.md`, `ARCHITECTURE.md`, `ANTI_ERROR_STANDARD.md`, `DEVELOPMENT_PROTOCOL.md` (this file), `PROJECT_STATE.md`, `DATA_MODEL.md`, `CALCULATION_ENGINE.md`, `DESIGN_SYSTEM.md`, `ADR/`, and `docs/security/*` are the canonical set. Code must conform to these documents; **an AI must never silently edit documentation to justify its own implementation** — a mismatch between code and doc is a signal to fix the code or raise the conflict (`/ANTI_ERROR_STANDARD.md` §4), not to quietly rewrite the doc.
48. **Anti-Duplication Rule**: `/ANTI_ERROR_STANDARD.md` §1 — binding, not restated here.
49. **Architectural Change Rule**: `/ANTI_ERROR_STANDARD.md` §4 — binding, not restated here.
