# DEVELOPMENT_LOG.md — Stepwise Historical Journal

This is an append-only record of what actually happened during development: completed stages, significant decisions and the reasoning behind them, verifications actually performed (and their results), problems found, and retrospective findings (`/ANTI_ERROR_STANDARD.md` §10).

This is **not** a mirror of git history (the commit log already covers "what changed, when") and **not** a per-file change log. An entry here is for something worth knowing without reading every commit: a phase completed, a conflict surfaced and resolved, a verification that passed or failed, a lesson learned. Entries are appended in chronological order and never rewritten — a correction to an earlier entry is a new entry, not an edit to the old one.

## DEV-003 — Design System Foundation

The first DEV task needing the Android Gradle Plugin. It immediately surfaced a real structural problem: adding `:core:designsystem` (needs `com.android.library`) to the same Gradle build as `:core:common` broke `:core:common`'s previously-VERIFIED build too, because Gradle configures the whole project tree by default regardless of which module's task is requested. First fix attempt: declare AGP/Compose plugins only inside `:core:designsystem`'s own build script, never at root, plus `org.gradle.configureondemand=true` in `gradle.properties`. This got local `:core:common` verification working again — but it took **14 real CI iterations** to get `:core:designsystem` itself to a genuinely green build, and most of that was a sustained misdiagnosis, not 14 independent bugs. Recorded here in full per `ANTI_ERROR_STANDARD.md` §10 — this is exactly the kind of finding a retrospective exists to preserve honestly, wrong turn included, not smoothed into a clean success story.

**Iteration 1** — `android-actions/setup-android@v4` (added preemptively as a safety net) tried to install a long-removed legacy SDK package and failed outright. Removed; GitHub-hosted runners already ship a working, license-accepted SDK.

**Iterations 2–8 — the misdiagnosis.** AGP moved to a 9.x major line; AGP 9.4.0 (checked live against the official release notes) requires Gradle ≥9.6.0, so the wrapper was bumped from 8.14.5. The very next CI run then failed inside the actual build with `Error resolving plugin [id: 'org.jetbrains.kotlin.android'] ... already on the classpath with an unknown version`. This was read as AGP 9's new "built-in Kotlin" support conflicting with the explicit plugin, and the next several iterations chased exactly that theory: removed `kotlin-android` explicitly (error changed to a `KotlinAndroidTarget`/`com.android.build.gradle.api.BaseVariant` crash); removed `kotlin-compose` too, hypothesizing it was the culprit (crash persisted with *no* Kotlin plugin applied at all — seemingly proof the crash lived inside AGP's own built-in-Kotlin bridging code, since it fired from `com.android.library` alone); researched Android's own built-in-Kotlin migration docs live and applied the documented opt-out, `android.builtInKotlin=false` (crash gone, but the *original* classpath error came back); researched further and found the docs also require `android.newDsl=false` alongside it (added — same original error persisted, unchanged). At that point, rather than guess a 6th time, downgraded to **AGP 8.13.2** (the last pre-9.0 line, no built-in-Kotlin code path to fight) specifically to rule the whole feature area out. The identical "already on the classpath" error reproduced under plain AGP 8.13.2 too — the theory had been wrong from iteration 2 onward. Not fully wasted work, though: this detour is what led to discovering iteration 12's real, unrelated Compose-BOM version-floor problem later, since it forced a clean AGP 8.x baseline first.

**Iterations 9–11 — the actual root cause.** With AGP no longer a suspect, the real mechanism became visible: root `build.gradle.kts` only ever declared `kotlin-jvm` as `apply false` (for `:core:common`'s benefit). `org.jetbrains.kotlin.jvm` and `org.jetbrains.kotlin.android` are different plugin IDs backed by the *same* underlying Kotlin Gradle Plugin artifact — resolving `kotlin-android` for the first time inside `:core:designsystem`'s own `plugins{}` block, with no matching root declaration, is what actually collided, regardless of AGP version. Declaring `kotlin-android`/`kotlin-compose` apply-false at root fixed that error but surfaced a new one (`NoClassDefFoundError` on `com.android.build.gradle.BaseExtension` — the Kotlin Android Gradle plugin's classes statically reference AGP classes, and AGP itself still wasn't resolved anywhere at root). The real, complete fix: declare `android.library` apply-false at root too — the standard Android Studio multi-module convention every earlier iteration had specifically avoided, in order to keep `:core:common` locally buildable in this `dl.google.com`-blocked sandbox. **That avoidance is what caused the entire bug class.** This is now a permanent, accepted trade-off, not a temporary one — see the retrospective note below.

**Iteration 12 — a real, separate finding.** Plugin resolution now clean, the build reached an actual AAR-metadata dependency check and failed there: Compose BOM `2026.08.00`'s own dependencies (`androidx.compose.animation:animation-core-android:1.12.0` and others) require AGP ≥9.1.0 and `compileSdk` ≥37. AGP 8.13.2 could never have satisfied this, independent of everything above. Moved back to AGP 9.4.0 (the version iterations 2–8 spent so long fighting) plus `compileSdk 37`.

**Iterations 13–14 — ordinary bugs, fixed normally.** First real compilation: a JVM-target mismatch (Java pinned to 17 via `compileOptions`, Kotlin defaulting to whatever JDK runs Gradle, 21 in CI) — fixed with `kotlin { jvmToolchain(17) }`, same pattern as `:core:common`. Then 47 detekt findings and, once those passed, 31 ktlint findings — both dominated by the same expected Compose-vs-JVM-linter friction (`FunctionNaming`/`LongParameterList` assuming camelCase/short signatures; Compose components are PascalCase and commonly take many parameters) — fixed with `config/detekt/detekt.yml` and a root `.editorconfig`, both `ignoreAnnotated`/`ignore_when_annotated_with = Composable`, inherited automatically by any future Compose module. Remaining findings were genuine and fixed as such: `MagicNumber` on color/easing literals (`ignorePropertyDeclaration: true`, plus extracting 4 named-argument color values that flag didn't cover into named constants) and `MatchingDeclarationName` on 3 files (renamed `Spacing.kt`→`StepwiseSpacing.kt`, `Motion.kt`→`StepwiseMotion.kt`; split `BottomNavigation.kt` so `StepwiseNavigationItem` has its own file). ktlint's wrapping violations (a multi-line call assigned via `=` must start on the next line) were fixed by hand against ktlint's exact reported line:column, since `ktlintFormat` itself can't run in this sandbox.

Built `:core:designsystem` (tokens: Color/Type/Spacing/Shape/Elevation/Motion, `StepwiseTheme`; 10 generic reusable components) per `DESIGN_SYSTEM.md`'s now-filled-in content. Deliberately deferred `StepwiseGoalCard`/`StepwiseTaskRow`/`StepwiseActivityRow` since they'd need to guess at domain-model shapes DEV-004 hasn't defined yet.

Regression check while touching `DESIGN_SYSTEM.md` found one more genuinely stale cross-reference (same bug class as the earlier `§25`/`§29` cases): its old scaffold cited `DEVELOPMENT_PROTOCOL.md` "rule C3–C4" for accessibility, off by one against the document's real current numbering (23–24). Checked the similar "A4/A5/A7/D2"-style citations elsewhere in the repo against the actual numbering too — they were all correct, so this was an isolated slip, not a repeat of the renumbering-collision pattern.

**Retrospective note (`ANTI_ERROR_STANDARD.md` §10):** the single most expensive mistake in this task was spending iterations 2–8 diagnosing a Gradle plugin-classpath collision as an AGP-version/built-in-Kotlin feature bug, when the actual signature — "already on the classpath with an unknown version" — is a generic Gradle plugin-resolution error with a well-known cause (a plugin ID resolved without a matching root-level declaration when another plugin ID from the same underlying artifact is already in play) that has nothing to do with AGP specifically. A durable rule for this was added to `ANTI_ERROR_STANDARD.md` as new §11, so a future DEV task (DEV-005 Room, DEV-007 Auth, DEV-015 `:app`, DEV-028 Widget — all future Android modules) checks the root apply-false declarations first rather than re-deriving this the hard way. Also newly true and worth stating plainly: this sandbox can no longer run *any* Gradle task locally, for any module — not just `:core:designsystem` — since `android.library` must now be apply-false'd at root and the root project is always configured. `PROJECT_STATE.md`'s VERIFICATION DEBT section records this as a permanent, accepted limitation, not a regression to chase further.

**CI confirmed green** (run [34966319372](https://github.com/ntegas/Stepwise/actions/runs/34966319372), commit `5ae16a5`, checked via the Actions API rather than assumed): full `build` (compile + unit tests + ktlintCheck + detekt) succeeded on `:core:designsystem` for the first time. DEV-003 is closed.
