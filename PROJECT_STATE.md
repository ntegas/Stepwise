## DEV-003 — Design System Foundation findings

Scoped per `/ROADMAP.md`'s DEV-003 description ("build semantic color tokens, typography, spacing, shapes, elevation, motion, light/dark theme, core reusable components... do not redesign every screen yet"). This is the first DEV task needing the Android Gradle Plugin, and it took **14 real CI iterations** to go green — most of that chasing a misdiagnosis, not fighting 14 independent bugs. Recorded here in full, honestly, per `ANTI_ERROR_STANDARD.md` §10 — the length and the wrong turn are exactly what a retrospective is for, not something to smooth over. Full push-by-push detail is in `DEVELOPMENT_LOG.md`; this is the organized summary.

**What actually happened, grouped by real cause (not 14 flat steps):**

1. **Iteration 1 — unrelated CI setup bug.** `android-actions/setup-android@v4` (added preemptively) tries to install a long-removed legacy SDK package and fails outright. Removed — GitHub-hosted runners already ship a working, license-accepted Android SDK, so the step was solving a problem that didn't exist.

2. **Iterations 2–8 — a genuine, sustained misdiagnosis.** The recurring error `org.jetbrains.kotlin.android ... already on the classpath with an unknown version` (and, separately, a `KotlinAndroidTarget`/`BaseVariant` crash) was read as AGP 9.4.0's new "built-in Kotlin" support being broken. Tried, in order: removing the explicit `kotlin-android` plugin, removing `kotlin-compose` too, confirming the crash persisted with neither applied (seemingly proving it was AGP's own bug), then `android.builtInKotlin=false` and `android.newDsl=false` (the documented opt-out pair) — the crash went away but the *original* classpath error came back identically. This was not wasted effort — downgrading to AGP 8.13.2 at the end of this chain (to escape the theory entirely) is what later exposed iteration 12's real, unrelated Compose-BOM finding — but the AGP-9-built-in-Kotlin theory itself was wrong throughout.

3. **Iterations 9–11 — the real plugin-resolution bug.** Root `build.gradle.kts` only ever declared `kotlin-jvm` as `apply false` (for `:core:common`). `org.jetbrains.kotlin.jvm` and `org.jetbrains.kotlin.android` are different plugin IDs backed by the same underlying Kotlin Gradle Plugin artifact — resolving `kotlin-android` for the first time inside `:core:designsystem`'s own `plugins{}` block collided with it, independent of AGP version (confirmed by reproducing the identical error under plain AGP 8.13.2). Fixing it required declaring **every** plugin used anywhere in the build — `kotlin-android`, `kotlin-compose`, and finally `android.library` (real AGP) itself — as `apply false` at root, the standard Android Studio multi-module convention every earlier iteration had deviated from specifically to keep `:core:common` locally buildable in this sandbox (`dl.google.com` blocked). That deviation is what caused the whole bug class. **This is a real, permanent trade-off, not a temporary one**: this sandbox can no longer build any part of this repository locally at all — see VERIFICATION DEBT below.

4. **Iteration 12 — a real, separate version-floor finding.** With plugin resolution finally clean, AGP 8.13.2 turned out to be flatly incompatible with Compose BOM `2026.08.00` anyway: its own dependencies (`androidx.compose.animation:animation-core-android:1.12.0` and others) require AGP ≥9.1.0 and `compileSdk` ≥37 — caught via a real CI AAR-metadata failure, not guessed. Moved back to **AGP 9.4.0** (the version iterations 2–8 spent so long fighting for the wrong reason) plus `compileSdk 37`.

5. **Iterations 13–14 — ordinary compile/lint fixes, nothing mysterious.** First real compilation surfaced a JVM-target mismatch (Java pinned to 17, Kotlin defaulting to 21 — fixed with `kotlin { jvmToolchain(17) }`, the same pattern `:core:common` uses); 47 detekt findings and 31 ktlint findings, both dominated by the same well-known Compose-vs-JVM-linter friction (`FunctionNaming`/`LongParameterList` expecting camelCase/short signatures, Compose using PascalCase components with many parameters) — fixed via `config/detekt/detekt.yml` (`ignoreAnnotated: ["Composable"]`) and a root `.editorconfig` (`ktlint_function_naming_ignore_when_annotated_with = Composable`), both now inherited by every future module automatically. The remaining findings were real: `MagicNumber` on color/easing literals (fixed via `ignorePropertyDeclaration` plus extracting 4 named-argument color values into named constants) and `MatchingDeclarationName` on 3 files (fixed via renames — `Spacing.kt`→`StepwiseSpacing.kt`, `Motion.kt`→`StepwiseMotion.kt` — and splitting `BottomNavigation.kt` so `StepwiseNavigationItem` has its own file).

**Built and now genuinely CI-verified**:
- `:core:designsystem` module: `com.android.library` 9.4.0 + Compose, `compileSdk 37`, `minSdk 26` (a stated, revisable technical default, not a product decision).
- Full token set + `StepwiseTheme` and 10 generic reusable components — see `/DESIGN_SYSTEM.md` for the complete breakdown, including which components (`StepwiseGoalCard`/`StepwiseTaskRow`/`StepwiseActivityRow`) were deliberately deferred to DEV-004+ because they'd need to guess at domain-model shapes that don't exist yet.

**Regression check found and fixed one more thing while touching `DESIGN_SYSTEM.md`**: its old scaffold cited `DEVELOPMENT_PROTOCOL.md` "rule C3–C4" for accessibility — off by one against the document's actual current numbering (rules 23–24, not 22–23). Checked the sibling "A4/A5/A7/D2"-style citations elsewhere in the repo against the real numbering too — those were all correct, so this was an isolated slip, not a systemic renumbering bug.

**Verification status**: `:core:designsystem` — compilation, ktlint, and detekt — is **VERIFIED**, confirmed via a real green GitHub Actions run (run [34966319372](https://github.com/ntegas/Stepwise/actions/runs/34966319372), commit `5ae16a5`, checked via the Actions API, not assumed). ## DEV-005 — Room Persistence Foundation findings

Scoped per `/ROADMAP.md`'s DEV-005 description: entities, relations, DAOs, indexes, converters, domain mappers, transactions, database configuration, migration strategy, database tests — Room entities kept separate from `:core:model`'s domain types, never reused directly. Not a checkpoint.

**Room-vs-KMP architecture decision, made explicitly rather than assumed**: the product owner was first asked (`AskUserQuestion`) whether `:core:database` should be a Kotlin Multiplatform module built on Room 3.0's KMP rewrite (`androidx.room3`), and initially chose that option on the stated rationale that it would give this sandbox genuine local JVM-target test coverage, unlike the Android-only artifacts this sandbox otherwise can't resolve (`dl.google.com` blocked). Before implementing, that rationale was checked live: `repo.maven.apache.org` returns 404 for `androidx.room:room-runtime` and `androidx.sqlite:sqlite-bundled` — these are Google-Maven-only artifacts regardless of target platform, so even a KMP module's JVM target would still need the blocked host, and the stated benefit would not actually materialize. This was surfaced back to the product owner (not silently implemented against a rationale already known to be false) via a second `AskUserQuestion`; the decision was then changed to a standard (non-KMP) Android module — simpler, with identical verification characteristics to `:core:designsystem` (CI-only). All real library versions (Room **2.8.5**, KSP **2.3.12**, Robolectric **4.17**) were checked live against Maven Central/plugin-portal metadata rather than assumed from training data — see `gradle/libs.versions.toml`'s comments for each.

**Deliverable**: `:core:database`, a new Android/Room module (`com.stepwise.core.database`, minSdk 26, compileSdk 37) depending only on `:core:model` — one Room entity + DAO pair per domain entity (14 total: Vision, LifeArea, Goal, Milestone, Project, Activity, Habit, Task, RecurrenceRule, RecurrenceOccurrence, Metric, GoalActivityLink, Session, SessionMetricValue), each with a `toDomain()`/`toEntity()` mapper pair so no Room type ever crosses `:core:database`'s boundary (`ARCHITECTURE.md` §5's module-boundary rule). `Converters` centralizes every cross-cutting `@TypeConverter` (Instant↔epoch-millis, `LocalDate`↔epoch-day, `LocalTime`↔second-of-day, all 6 domain enums via `.name`/`valueOf()`, `RecurrencePattern` via a custom colon-delimited string encoding) in one place rather than per-entity, per `DEVELOPMENT_PROTOCOL.md`'s centralization rule. `SyncColumns` (`@Embedded` into every syncable entity) centralizes the 3 sync-metadata columns the same way. `SessionDao.upsertSessionWithMetricValues` is the one `@Transaction`-boundary write DEV-005 requires — a Session and every one of its metric-value rows commit atomically, matching `ARCHITECTURE.md` §9.0. `STEPWISE_DATABASE_MIGRATIONS: Array<Migration> = emptyArray()` and `buildStepwiseDatabase()` establish the migration-array and single-builder-site conventions now (schema version 1, nothing to migrate from yet) so they exist before they're actually needed, rather than invented ad hoc at the first real schema change. `exportSchema = true` (Room's default, kept rather than turned off) writes every schema version to `core/database/schemas/` via the `ksp { arg("room.schemaLocation", ...) }` line, which is what makes a real future migration possible instead of a guess.

**A real bug found and fixed while writing this layer, not left in place**: `Vision` in `:core:model` (written at DEV-004) carried both its own `updatedAt: Instant` field and a `sync: SyncMetadata` (which itself has `updatedAt`) — a genuine duplicate column, not intentional design (`DATA_MODEL.md`'s `visions` field list has exactly one `updated_at`). Found while writing `VisionEntity`'s mapper and noticing the redundancy; fixed by removing the field from `Vision` (`StrategicLayer.kt`) and its corresponding mapper line. Checked via `Grep` across every other entity for the same pattern (`Goal`/`Task`'s `createdAt` is a legitimately distinct, separate field from `sync.updatedAt`, so left alone) — no other instance found.

**A fragile test pattern found during review and fixed before committing**: the Task-inbox-query test originally read a `Flow`'s single emission via `launch(Dispatchers.Unconfined) { flow.collect { ... } }` immediately followed by `job.cancel()` — a pattern that depends on `Unconfined`'s synchronous-dispatch behavior lining up exactly right and is not a standard, guaranteed-correct way to read one value from a `Flow`. Replaced with `kotlinx.coroutines.flow.Flow.first()` before committing, since this module cannot be built locally at all (below) and a subtle test-infrastructure bug would only surface as a flaky or wrongly-passing CI result, not a local failure caught early.

**Verification status — CI-only, matching `:core:designsystem`'s precedent, stated plainly rather than assumed**: `:core:database` itself applies `com.android.library` in its own `build.gradle.kts`, so — unlike `:core:model` — the DEV-004 local-verification workaround (temporarily commenting out root `build.gradle.kts`'s `android.library apply false` line) does not apply here: any local Gradle invocation targeting this module still needs to resolve AGP against the blocked `dl.google.com`, regardless of the root file's state. No local build, test run, ktlint, or detekt pass was possible for this module in this sandbox. In place of that, every file was read back and manually reviewed line-by-line for Room-annotation correctness, `TypeConverter` registration completeness (cross-checked against every field type each entity uses), mapper field-by-field correctness (each `toDomain()`/`toEntity()` pair checked against its domain type's constructor), and index placement (every foreign-key-shaped column indexed) before committing — the two defects found during that review (the `Vision` duplicate field and the fragile `Flow` test) are documented above rather than silently fixed with no record. Real GitHub Actions CI is the sole verification this module receives.

**First real CI run (34985664638, commit `2f3448f`) failed** — a genuine gap in the manual review, not a false alarm: detekt's `TooManyFunctions` fired on `StepwiseDatabase` (13 DAO-accessor functions against a default threshold of 11) and on `Converters` (20 converter functions against the same threshold), plus `SpreadOperator` on `buildStepwiseDatabase`'s `.addMigrations(*STEPWISE_DATABASE_MIGRATIONS)` vararg call — all three are the expected, legitimate shape of this exact code (one accessor per real DAO, one converter class centralizing every `@TypeConverter` per `DEVELOPMENT_PROTOCOL.md`'s own centralization rule, Room's own vararg API), not design smells to restructure around. Fixed with a targeted, justified `@Suppress` on each declaration (the same treatment `GoalEntity`/`TaskEntity` already use for `LongParameterList`) rather than loosening `detekt.yml`'s thresholds project-wide, which would have hidden the rule for code that might actually deserve it. Manual review also caught, before this push, that `StepwiseDatabaseTest.kt`'s import order was wrong per this project's real ktlint import-layout rule, confirmed empirically at DEV-004: a bare `kotlin.**` import (here, `kotlin.time.Instant`) always sorts as its own group after every other import, including `org.*` — not before it, as it had been written.

**Second real CI run (34986280376, commit `8580047`) also failed**, on a genuinely new issue the first run never reached (detekt now passed clean): ktlint's wrapping rule flagged 4 lines in `StepwiseDatabaseTest.kt` ("Expected newline before '.'") — every one of them a fully-qualified `com.stepwise.core.model.X(...)` constructor call used inline instead of through an import (`Vision`, `Session`, `SessionMetricValue` twice), which ktlint's multi-line-call wrapping rule treats as an unwrapped member-access chain once the argument list itself spans multiple lines. Fixed by importing those 5 types (`Vision`, `Goal`, `Session`, `SessionMetricValue`, `Task`) properly and using their simple names, matching every other file in this module — there was no actual name collision motivating the fully-qualified form in the first place (`VisionEntity`/`GoalEntity`/etc. live in the same file but don't share a name with their domain counterparts).

**Third real CI run (34986735142, commit `4e049b4`) also failed**, this time on an actual compiler error rather than lint — `Converters.kt:30`: "Return type mismatch: expected 'Int?', actual 'Long?'" in `localDateToEpochDay`. `kotlinx-datetime` 0.8.0's `LocalDate.toEpochDays()` returns `Long`, not `Int` as assumed when writing the converter (a genuine wrong assumption, not a version-drift issue — confirmed by extracting and `javap`-inspecting the actual cached `kotlinx-datetime-jvm-0.8.0.jar` in this sandbox, which resolves from Maven Central and was already present locally from `:core:common`'s own dependency on it). Fixed by changing `localDateToEpochDay`/`epochDayToLocalDate` to use `Long` throughout, matching `Instant`'s epoch-millis columns' own type. This is the first defect in this module a genuinely local check (bytecode inspection of the real dependency jar, not just reading source) could have caught before pushing, and should have been checked this way from the start rather than assumed from memory of the API shape.

**Fourth real CI run (34987253276, commit `f81a209`) also failed**, past compilation this time: `:core:database:testDebugUnitTest` failed both test classes (`RecurrencePatternConverterTest` and `StepwiseDatabaseTest`) with `initializationError` / `java.lang.UnsupportedClassVersionError` at class-load time — before any test method ran, and notably including the plain-JUnit4, no-Android-dependency `RecurrencePatternConverterTest`, so the cause was module-wide, not Robolectric-specific. Root cause: `:core:database/build.gradle.kts` had copied `:core:designsystem`'s `jvmToolchain(17)` (a choice that module's own tests never actually exercised, having no `Test` task with real runtime dependencies), while `:core:model` — the project's other module with real, CI-verified tests — uses `jvmToolchain(21)`, matching the single JDK the CI workflow actually installs ("Set up JDK 21"). With a separately-provisioned JDK 17 toolchain, something on the Robolectric/androidx-test/JUnit4 test runtime classpath needed a newer JVM than that toolchain supplied. Fixed by moving `:core:database` to `jvmToolchain(21)` (and `compileOptions` to `VERSION_21`) to match `:core:model` and the CI environment, rather than chasing which exact dependency required it.

**Fifth real CI run (34987949082, commit `ca829eb`) also failed**, and this one confirmed the JDK-21 fix worked as intended: `RecurrencePatternConverterTest` (plain JUnit4, no Robolectric) now passed all 5 tests — the `UnsupportedClassVersionError` is gone. The remaining failure was new and specific to Robolectric: all 4 `StepwiseDatabaseTest` tests failed identically with `java.lang.RuntimeException` at `AndroidInterceptors.java` caused by `java.lang.IllegalAccessException` at `Reflection.java` — the well-known, Robolectric-documented (not project-specific) JDK 17+/21 strong-encapsulation problem: Robolectric's sandbox classloader reflectively opens JDK internals (`java.lang`, `java.util`, etc.) that the JPMS module system blocks by default unless the test JVM is launched with the corresponding `--add-opens` flags. Fixed by adding Robolectric's standard `--add-opens` set to `:core:database`'s `Test` tasks via `tasks.withType<Test>().configureEach { jvmArgs(...) }`.
